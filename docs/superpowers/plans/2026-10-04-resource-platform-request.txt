APPROVED PRODUCT DIRECTION

Build a highly customizable, FiveM-style resource platform.

Lua is the first supported resource language. Design runtime boundaries so JavaScript and C# can be added later, but do not implement those runtimes now. Python is not the selected resource language.

Closely follow FiveM’s developer-facing operating model:
- Resources and manifests.
- Separate client, server and shared scripts.
- Resource dependencies and exports.
- Local and network events.
- Replicated state with explicit ownership.
- Server configuration.
- Resource start, stop, restart and ensure behavior.
- Server-selected client resources.
- Automatic client downloads and persistent cache reuse.

Research current official Cfx documentation and relevant citizenfx source. Record a concise compatibility matrix explaining supported behavior and deliberate differences. IMPLEMENTATION SCOPE

1. Resource manifests and lifecycle

Implement a versioned resource contract describing:
- Identity, version and required engine/API capabilities.
- Client, server and shared script entry points.
- Downloadable assets and files.
- Dependencies and exported interfaces.
- Permissions or capabilities where relevant.

Validate paths, duplicates, dependencies, cycles and compatibility.

Provide dependency-aware start/stop/restart/ensure behavior and useful diagnostics. Resource failure must be contained. Cleanup must be enforced by the engine, including entities, callbacks, timers, UI, audio and engine overrides; do not rely solely on script cleanup.

Preserve existing local Lua mods through a documented compatibility or migration path.

2. Dedicated-server Lua runtime

Add an actual headless resource host to skate-server.

Support server scripts for game rules, challenges, commands, permissions and resource-scoped persistence. Separate server capabilities from client-only rendering, camera, input and presentation APIs.

The dedicated server remains the authority for shared state and authorization. Existing SDK assumptions about player-hosted sessions or transferring authority between players must be adapted deliberately.

3. Client resource synchronization and activation

On connection:
- Negotiate the server’s required resource set and compatible versions.
- Resolve dependencies and required content.
- Reuse verified cached content.
- Download missing content.
- Validate it before publication and execution.
- Activate client/shared resources in the correct order.
- Admit the player to gameplay only after required resources are ready.

Server-only scripts, secrets and private server configuration must never enter the client download set.

Use a separate bounded resource-transfer path so downloads do not interfere with movement traffic. Prefer an appropriate HTTP(S) content path after assessing existing dependencies and hosting requirements.

Handle cancellation, interrupted downloads, corrupt content, failed startup, disconnects, resource updates and reconnects coherently. Failed updates must not leave a partially published resource set.

4. Persistent content cache and client audit

Implement persistent, immutable content storage using full cryptographic digests and canonical cross-platform path/manifest rules.

Reuse identical content across:
- Reconnects.
- Client restarts.
- Different servers.
- Resource versions containing unchanged files.

Resource names and version labels alone must never determine cache identity.

Maintain a persistent client resource inventory/history with:
- Resource identity and version.
- Exact content digests.
- Server/source provenance.
- Requested capabilities and applicable grants.
- Verification results.
- Download size.
- Activation/failure history.

Provide a usable way to inspect this information and manage cached content. Bound cache size and history growth.

Share cached immutable bytes across servers, while keeping script state, permission decisions and private server data appropriately isolated. Leaving a server must unload its running resources and restore owned overrides without deleting reusable content.

A client inventory is not proof against a modified client; do not treat it as anti-cheat attestation.

5. Resource networking

Implement the events, exports and replicated state needed by resources.

Define delivery and ownership semantics. Validate client requests on the server, derive sender identity from the connection, and enforce payload/rate/resource limits.

Prevent one resource from impersonating another or mutating state it does not own. Handle resource generations so stale messages from stopped/restarted resources cannot affect new instances.

Keep this layer compatible with both direct UDP and a future Steam dedicated transport.

6. Extensible engine API

Build on existing generic Lua APIs and expose customization through documented, versioned capabilities covering:
- Entities and lifecycle.
- Physics and skating controls.
- Animation.
- Camera and input.
- UI and audio.
- Maps/world content.
- Scoring and game-mode rules.
- Networking and resource persistence.

Audit what already exists, connect it to the new client/server resource hosts, and implement missing primitives needed for complete working resources.

Keep game-mode rules in Lua where practical. Avoid hardcoding special behavior for individual resource IDs.

Do not interpret “expose everything” as arbitrary process memory access or automatically downloading native DLL/SO code. Use supported engine interfaces, ownership and validation. Document real API limitations honestly rather than claiming complete customization prematurely.

7. Working resources and developer experience

Ship redistributable example resources that exercise the system end to end, including:
- A server-controlled skating challenge or competition.
- Downloadable client Lua and custom UI/assets.
- A dependency/export interaction.
- Validated client-to-server events.
- Replicated state.
- Resource-scoped persistent data.
- Lifecycle commands and clean shutdown.

Document resource authoring, server setup, language/API boundaries, resource distribution, cache/audit behavior, troubleshooting and migration from existing mods.

KNOWN CODEBASE GAPS TO VERIFY

Earlier inspection found:
- skate-mods manifests currently have a single entry point rather than separate client/server/shared entries.
- archive::Cache is path-keyed, extracts into a session directory, and deletes that directory on drop. It is not the required persistent cross-server cache.
- Existing package fingerprints hash native path strings and reduce a BLAKE3 digest to u64. Do not reuse that representation as a portable persistent content/security identity.
- Existing capability discovery describes compiled features rather than per-resource permission grants.
- Dedicated clients currently skip mod execution/replication.
- Dedicated networking currently rejects arbitrary application records and blob transfers.
- skate-server currently has no mod-runtime dependency.

Inspect these in current source before choosing changes. Preserve legacy networking and local mod behavior.
